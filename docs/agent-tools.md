# Cosmos Agent tools and permissions

The bundled/source Cosmos Agent advertises ten short tools. The native MCP producer maps them to existing workspace APIs, checks the canonical leaf permissions, signs conversation identity and sanitizes results. There is no second executable tool registry. Plain system OpenCode is launched unchanged and does not receive these tools.

## Tools

- `cosmos_context(target?, client?)`: current target, view, live client selection/candidates, this conversation's unfinished tasks, ownership state, paused flag, `allowed_next` and recent output. `target` accepts `%pane` or displayed `session:pane`. The first default target is the launch source; otherwise the selected client's active pane can supply it. It never lists the Actions catalog.
- `cosmos_observe(target?, layers?, region?, observation?, view?)`: fresh positioned text/presentation/inferred-control evidence. Optional `observation` is a prior short handle for unchanged detection; `view="screen"` is the default, while `view="delta"` returns positioned changes against the previous delta observation. Styled characters are not image pixels or Reader overlay semantics.
- `cosmos_step(target?, text?, submit?, keys?, mouse?, observation?, wait_ms?, full?)`: literal single-line paste and optional Enter, or ordered keys, or a mouse event, or a wait-only observation. Use exactly one input form. Mouse requires a fresh observation handle and one-based content-cell coordinates. The adapter supplies the held pane token. Backend checks revocation before each stage. A Tmux copy/view mode is cleared before input and reported as `mode_cleared`; the observation includes `pane_in_mode` and the visible screen mode. Partial delivery lists delivered stages, which must not be blindly repeated. `full=true` requests the full post-paste observation; keys/mouse return updated context and bounded recent evidence, with full inspection available through `cosmos_observe`.
- `cosmos_control(operation, ...)`: `allow(target, operations, seconds)` gets one explicit, time-limited allowance for a planned burst of terminal-control operations on a pane; it lists the operations and lifetime, covers later `begin` calls, and expires automatically (30–3600 seconds). `begin(target, observation, label, takeover?)` acquires a temporary pane-control lease after a fresh observation, without creating a Tasks row; paused takeover requires `takeover=true` and a fresh approval, which an allowance cannot bypass. `release` ends own control; `end` ends this conversation's own/legacy control without a token; `status` lists pane control leases.
- `cosmos_task(operation, ...)`: persistent tasks only. `list` returns current conversation tasks; `resume(handle, reason)` resumes a paused task and, after the single user confirmation, acquires fresh control; `finish(handle, outcome, summary)` reports evidence and deletes finished one-off tasks; `schedule(target, goal, schedule, mode)`; `history(handle)`; `cancel(handle)` cancels and deletes; `delete(handle)` deletes an already ended task. Immediate takeover belongs to `cosmos_control`, not `cosmos_task`.
- `cosmos_workspace(operation, ...)`: `list`, `begin(task)`, `release`, `terminal(target)`, `session(target,name)`, `rename(target,name)`, `focus(target,client?)`, `export(session,output?)`. A workspace grant covers creation/rename/focus only. Terminal input, close, interruption, privacy and unrelated Actions remain excluded. Creation returns actual startup/cwd data and a reusable observation.
- `cosmos_open(path,target,client?)`: opens a supported document or image (PNG, JPEG, WebP, PDF, EPUB, Markdown, HTML) in Reader, or a directory in Files. Use it instead of terminal `cat`/decode/render attempts. A pending request is not proof of loading; use `cosmos_actions events` for actual Reader lifecycle.
- `cosmos_history(target?,query?,limit?,cursor?)`: bounded immutable scrollback pages; follow `next_cursor` for older retained rows. Privacy is checked on every page.
- `cosmos_actions(operation, ...)`: `discover(scope?,category?,client?)`, `invoke(id,scope,params?,client?)`, `events(request_id,client?,wait_ms?)`. Reader lifecycle events are emitted by the Reader itself. A routed action is not proof that a modal completed.
- `cosmos_watch(operation, ...)`: `begin(target,condition,text?,timeout_seconds?)`, `list`, `cancel(handle)` where handle is the returned watch ID. Conditions include literal `text_present`/`text_absent`, `regex_present`/`regex_absent` (inline flags supported, 256-character pattern, 20 ms search limit), `changed`, `program_changed` and `bash_prompt`. Background waiting releases held input control. Conditions/timers never resume a manually paused task.

The advertised schemas are authoritative for optional arguments. Old internal MCP methods remain available to the transport for compatibility, but are not duplicate model catalog entries.

## Results and internal handles

`cosmos_context` returns a compact context directly. Other operations return `{result, context}` with a refreshed context after execution, including structured recoverable errors. If the context transport is unavailable, the operation's result is retained and context explicitly reports unavailable; do not repeat a potentially completed mutation. A context read permission is checked before these operations, so an explicit denial cannot be bypassed by obtaining the same data as a sidecar.

Context lists at most eight unfinished tasks, with a total/truncation indicator. Recent output is at most eight nonblank rows and 1024 UTF-8 bytes, plus cursor, region, truncation and observation handle. It is terminal evidence, not a command-completion claim. Unknown targets return candidates. Disconnected/ambiguous clients return candidate IDs and never silently direct a mutation elsewhere. The task handle in the resume entry can be passed directly to `cosmos_task resume`, avoiding Actions discovery.

Model-visible observation handles (`o_...`) and task handles (`t_...`) are bound to the native conversation and Agent. The adapter retains raw snapshot identities, task revisions/challenges and control capabilities. Control/workspace tokens are absent from model schemas and results. Control leases are not task rows; only persistent scheduled/waiting work gets a task handle. Handle tables hold at most 128 observations/tasks per conversation/Agent; at most 128 such states are retained. Eviction/restart fails closed and requires fresh discovery. Handles are not persistent authorization and must not be copied to skills.

Manual pause invalidates backend delivery immediately. Paused context discards adapter-held pane input rights. A persistent-task resume confirmation also authorizes one fresh takeover and obtains a new token; the old token is never restored. A control-only paused pane can be taken over with a new `cosmos_control begin(takeover=true)` approval; an allowance is not a takeover grant. An explicit allowance is bound to one conversation/Agent/pane, shows its planned operations and lifetime, and expires automatically; it covers only later control acquisitions/input and never Shell, Actions, close or interruption. Explicit deny policies apply to both public short aliases and canonical compatibility actions. The producer's same-conversation task grants never authorize another pane or Agent.

## Four authorization classes

Directory reads cover the displayed directory and all descendants. Remembering a read scope stores `cosmos_directory_read` for that project. It is shared by read/list/glob/grep and recognized read-only Shell toolsets within approved roots. Existing recursive `external_directory` grants also satisfy these read checks, so tool changes and nested directories do not require another approval. Writes, scripts, unknown commands and interruption remain separate. Explicit existing search-pattern denies remain honored. When configured read/access denies exist, directory grants do not automatically approve Shell: its lexical scope cannot enforce per-file exclusions, so a separate Shell decision remains necessary. Conservative exact-file scopes at a relative project root remain exact-file scopes.

Terminal control approval covers acquisition, ordinary bounded input, own release/end of that control, and cleanup of a legacy own control in the identified conversation/control lease/terminal; it is separate from persistent task rows. Release/end never require a second control confirmation. The acquisition grant expires on release, finish, control change or manual pause and is never saved as a project wildcard. C-c/C-z/C-d and resource closing/interruption require separate one-shot confirmation even under a general allow policy.

Filesystem investigation is explicitly routed by the Agent prompt and Cosmos-only Shell tool description to native read/listing, glob and grep (with path/include/limit); changes use edit/write/patch. Recognized read-only pipelines such as `grep ... | head; echo ...; grep ...` reuse approved recursive directory roots; other Shell commands retain their execution approval. Prompt guidance is not an execution classifier or a guarantee of the model's next tool choice. When a dedicated tool cannot express an operation, the Agent must explain that limitation and request bounded Shell execution. Long approval content scrolls inside the compact card without shrinking wrapped lines; confirmation buttons remain outside the scroll area.

Host writes/execution show affected path/command and working directory where available. Mixed commands and `python -c` are execution capabilities, never read-only directory grants. New Cosmos host edit/write/patch confirmations remain one-shot. Shell supports Always for a structured toolset and directory scope, or for one exact invocation as described below; it never creates a new unrestricted program-prefix wildcard. Existing remembered rules remain effective until explicitly revoked; this is not an OS sandbox.

Workspace management covers creation, rename and focus, with its own task capability; it excludes close, input, interruption, privacy and unrelated Actions. Other actions retain individual permission checks. Every confirmation presentation states category, scope, lifetime and write effect. Manual task resumption is a separate blue/info card, defaults to Keep paused and cannot be remembered.

## Inspect and revoke saved rules

Open Agent Settings → Permissions, Ctrl+P → Cosmos permissions, or `/permissions`. The dialog lists the current project's saved approvals grouped by capability, including legacy Shell/action wildcard rules. Opening or inspecting does not change any rule. Selecting a rule shows its scope, lifetime and write impact; Keep approval is the default. Revoke re-fetches and verifies the exact selected ID/action/resource before deleting that one rule through OpenCode's existing saved-permission API. There is no bulk migration or automatic cleanup.

Revocation affects subsequent evaluations; it does not undo filesystem changes, kill running commands, or terminate an already-held transient task capability. Use COSMOS → Agent tasks to pause/finish those tasks. Configured allow/deny policies remain in the Agent config and are not silently rewritten by this dialog.

## Remembered Shell toolsets and scope

A Shell confirmation offers **Allow once / Always allow / Reject** with the toolset, canonical working directory, literal path roots, write impact and lifetime shown. Always stores a `cosmos_shell_scope` rule for the current project, until explicitly revoked in Permissions. Subsequent invocations reuse it only when the shell/workdir match, every tool is in the approved set, every resolved literal argument path is under an approved directory (or is the exact approved file), and the write capability is covered. A subset of the approved tools can be reused; adding a tool, changing cwd or reaching a new path requires approval again. Existing Shell-prefix grants are retained unchanged and remain inspectable/revocable. Configured explicit denies still take priority.

The bounded toolset recognizer handles common inspection tools (`grep`, `rg`, `head`, `cat`, etc.) and basic file-operation tools (`mkdir`, `touch`, `cp`, `mv`, `rm`, `rmdir`). It permits ordinary pipes/separators when all constituent commands are recognized and allows stderr discard to `/dev/null`. Unknown options/tools, interpreters, variable/command expansion, directory changes and other redirection use an **exact invocation** scope instead. Those approvals match the same command text, canonical shell and cwd; the stored rule contains a digest, not source code or credentials. Exact scopes are identified by tool names and a short digest in Permissions. This preserves approval for repeated Python/script commands without silently allowing arbitrary future code. Recognized direct interruption/stop commands (`kill`, `pkill`, service-stop commands and Tmux kill operations) still force one-shot confirmation and cannot be remembered.

These are intent scopes for trusted host execution, not filesystem isolation: tool implementations, scripts, aliases and environment can have effects beyond lexical operands. Exact-mode commands can refer to locations beyond cwd as shown in their command text. The confirmation does not claim a system sandbox, and remembering Shell execution is distinct from the native directory-read grant, except that recognized read-only toolsets can reuse approved recursive directory roots.

`PYTHONPATH=python .venv/bin/python dev/validate_agent_real_api.py --real-api` is an explicitly opt-in, billed provider probe. It reads existing DeepSeek credentials into a temporary private profile, creates a separate Tmux service, tests short Cosmos tools plus native read/glob/grep, verifies actual fixture output, reports tool statuses, and cleans up only its temporary service. It does not print keys or operate live user panes/grants. The default fake-provider validation remains available for ordinary development.


## Global policies and AI approval

Agent **Settings → Global Cosmos approvals** stores private profile-wide preferences in `approval.json`. Each Cosmos tool group (context, observation, history, watch, tasks, workspace, control, actions, open) has Default / Allow / Ask / Deny. Allowing watch avoids repeated registration approvals across projects. Default preserves existing native rules; Ask always requests a human decision; Deny blocks the group. Changes affect subsequent evaluations without reopening the Agent. Saved project grants remain separately inspectable in Permissions. Explicit configured denies and human-only resume/interruption checks remain authoritative.

The optional **AI approval** mode first authorizes the current working directory, shown in the mode picker. **Approved working scopes** can edit the directory list. It uses three stages: sandbox execution and deterministic rules inside the approved scope; an independent reviewer for boundary exceptions; human confirmation for major operations. Ordinary reads/file edits, Python and test execution within scope need no reviewer API call.

On Linux, approved Shell requests run through `/usr/bin/bwrap`: workspace and a private per-scope temporary directory are writable, system runtime directories are read-only, network/PID namespaces are isolated, provider/Agent credentials and shell startup environment are removed. Host home/config paths are not mounted; known private directories inside the workspace are hidden and its existing Git metadata is read-only. `$TMPDIR` points to the private scratch directory; sandbox `/tmp` is ephemeral. This confines arbitrary Python rather than trusting its cwd. Bubblewrap and working user namespaces are required; failure never silently falls back to host execution. The currently running shell is not sandboxed retroactively.

Shell defaults to `sandbox:true` within an approved scope. For a necessary host boundary exception, request `sandbox:false`; its exact command enters independent review, including when an old broad Shell approval exists. Native read/edit requests outside approved roots also enter review. Boundary review is not a permanent directory or Shell wildcard grant. A missing/denied path in the sandbox does not automatically replay a command on the host: inspect partial results first. Recognized destructive requests, publication, privilege/service changes, credential/policy access and paused-task recovery remain human decisions. Arbitrary code can modify the user-authorized workspace; the sandbox enforces host boundaries, not the semantic intent of every instruction in a script. Native filesystem rules resolve symlinks; arbitrary code in an independently approved host exception is trusted execution, not confined by the earlier sandbox.

The separate reviewer module defaults to provider `deepseek`, model `deepseek-flash`, thinking `high`. Model/provider/OpenAI-compatible endpoint and thinking strength are configurable in that panel. Credentials come from the private Cosmos provider credential map; missing credentials fall back to a human decision. Enabling the mode permits sending boundary exception requests to this configured reviewer and incurs provider usage. No real-provider request is made just by opening Settings.

Reviewer calls have no tools and receive only a bounded action/command/path summary, not the executing Agent's conversation, rationale, or claimed safety. The reviewer cannot change policies or issue execution itself. Known provider secrets are redacted; no file contents are included. Existing native read/tool allowances run without an additional AI call; an exact pending request is deduplicated briefly. Requests use a 10-second timeout and at most 1024 output tokens; failure, malformed responses or uncertainty fall back to the native permission card. AI approval authorizes only the current request, never a new permanent wildcard grant. A bounded `approval-audit.jsonl` records decision source (policy/rule/AI), effect and a fixed summary, excluding commands, content and credentials.

Validation includes real Bubblewrap Python/test execution, host-path/network/credential isolation and the actual native Shell spawn seam, plus the independent request format with a mock provider, no-call rule paths, scoped paths and symlink escapes, native permission-service deny/resume enforcement, and actual Settings keyboard interaction with a temporary profile. It does not claim real-provider latency or model safety accuracy.
