# 架构边界修订：Cosmos 自有核心与稳定终端底层

最新补充（2026-10-22）：采用 Python + Textual 负责 UI 与功能编排，Tmux 保留为会话/终端后端。详见 [Python + Textual 迁移](Python-Textual迁移.md)，其选型与迁移边界优先于下文早期 Rust UI 描述。

日期：2026-10-21。依据用户最新澄清：不是以修改 Tmux 为产品实现主体，而是由 Cosmos 自行实现大部分逻辑，同时重用 Tmux 已验证稳定的部分。

本文件优先于《实施方案 v0.1》和早期研究中的“定制 Tmux 壳扩展”“先修改客户端绘制层”等路线表述。既有产品行为与视觉约束继续保留。

## 实现归属

Cosmos 自行负责：Mod 协议与加载、配置、事件、操作、键位语义、输入目标、焦点、视图生命周期、布局、面板、通知、主题、缓存、文件/查看器/Agent 协作，以及后续客户端合成与呈现。

稳定终端底层负责：PTY、应用进程、终端协议状态、持续会话、重连等成熟基础能力。Tmux 的这些能力很重要，但不让 Tmux 的命令表、popup 或模式结构定义 Cosmos 的业务模型。

目前以 Tmux 进程适配器保留持续会话体验；后续通过独立后端接口决定哪些能力继续调用、哪些稳定组件提取复用。尚未实现 Tmux 库化、终端引擎提取或新的原生多路复用器，不能把接口抽象说成这些工作已经完成。

## 当前代码边界

- `backend.rs` 定义会话后端接口，应用入口与协调请求通过接口访问底层。
- `backends/tmux.rs` 为当前兼容适配器。后续更换引擎不应重写 Mod、事件、设置和 UI 状态。
- `ui.rs`、`terminal_ui.rs`、`events.rs`、`mods.rs` 是 Cosmos 自有逻辑。已验证在 Tmux 不可用时，独立面板、设置、事件和示例 Mod 仍能运行。
- 当前会话内的 `Leader p` 暂借 Tmux popup 提供一个终端表面，内部全部面板逻辑由 Cosmos 提供。它只是过渡呈现适配，不是长期合成架构。
- 自有合成器接管后，以同一 UI 状态、焦点与动作模型实现面板/侧栏/通知；不继续把业务堆进 Tmux 补丁。

## panel 闪退修复

根因是运行中的协调服务为协议 1.0，而新 panel 需要 1.1 接口。旧健康检查只检查 alive/ready。接口失败后 popup 子进程退出，宿主自动关闭，错误不可见。

修复：UI 接管终端前先检查协议版本与必要能力；popup 模式加载失败时保留错误直到 Enter 关闭，并写运行目录的 panel-error.log。替换磁盘上的可执行文件不会替换已运行服务，诊断中显式返回协议能力。

当前旧进程身份已验证，并确认无已加载 Mod 和内存通知后更新协调服务。现有 Tmux 窗格与应用 PID 前后核对一致。

## 后续实施顺序

先完善 Cosmos 自有呈现表面与合成接口，定义终端底层向其提供的 grid/光标/尺寸/事件能力；再为稳定底层建立桥接。不得通过重新拼装未经解析的 PTY 文本伪装完整终端，也不把客户端合成问题退化成不断添加 Tmux popup。
